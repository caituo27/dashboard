# 前端分支相对 main 的完整改动说明

核对日期：2026 年 9 月 12 日

分支：`feat/admin-dashboard-shared-mock`

范围：**整个分支相对已获取的远程 main（`origin/main`：`252cbca`）的变化**，包括管理端、C 端、Mock 服务、测试与部署文件，不限于最后一次提交。当前分支已通过 `e7cbff4` 合并该 main。本说明包含合并后尚待本次提交的修改；没有再次获取远程，因此不代表远程此刻没有更新。

> 阅读结论：目前实现了“真实业务数据＋可操作的生成记录”的展示平台。任务、执行、资金大部分有明细关联，但 Agent 总量、行为分析和用户画像仍是生成数据。它可以展示业务流程，不能把混合后的指标作为实际用户规模或真实收入证明。

## 本次补充了什么

1. **停止自动发布任务**：截止时间固定为北京时间 2026 年 9 月 12 日 18:44:05，保留 85,804 个基础生成任务。重启或重新部署不会重新开始增长。真实任务仍可正常发布。
2. **已有订单继续推进**：截止时约 1,713,213 条基础执行。自动执行仍可增长至现有任务分组的上限 1,716,082 条，之后停止；已接任务继续提交、验收和结算。显式模拟接单另按剩余名额校验。
3. **重写任务内容**：参考用户提供的任务表结构，重写 12 类场景，补齐背景、输入、交付格式和验收条件，不导入表格原任务。原分类、奖励、时间线规则保留。
4. **补齐验收结果**：按执行记录返回提交说明、Token 用量和提交时间；提供 Markdown 交付内容、CSV 交付明细，设计类另有 SVG 结构图。文件可下载，大小与 SHA-256 按实际内容计算。Token 和交付仍是生成内容，不是实际 Agent 执行证明。
5. **修复内部编号外露**：申诉详情标题、信息区和部分弹窗统一显示业务编号；操作仍使用原内部 ID。
6. **减少重复计算**：快照先查缓存；事件按日复用；任务与资金汇总对象复用，减少每次切换、轮询时的重复生成。

## 3. 数据分成哪几类

### A. 真实后端数据

来源是原有 `/sprix-api/` 后端接口，包括任务汇总、任务详情与执行记录、验收、申诉、结算和提现记录。没有把真实用户替换成虚构用户，也没有把真实金额统一改成生成金额。

### B. 基础生成数据

独立 HTTP 服务 `/mock-api/` 根据时间、固定 ID 和规则构造任务、执行、用户、结算等数据。大量基础记录是按规则计算出来的，不是实际数据库里新增了 170 万笔真实订单。

### C. 用户在 Mock 上操作产生的数据

管理端编辑、下线、审核以及本地 C 端模拟接单，写入独立状态文件。它们会覆盖对应基础规则，并影响之后的页面查询。

真实和生成数据**没有在真实数据库内合并**。页面将两套结果组合展示。

### 时间范围与金额口径

- 近 7 天／近 30 天控制趋势和行为分析，包含今天；累计订单、累计金额不随这个选项变成期间总额。
- “已完成订单金额”当前实际取已入账结算记录。如果真实后端存在“已完成但还没入账”的订单，它不会进入这个金额。
- 最新任务按发布时间排序，旧任务有新接单不会因此成为最新发布任务。
- 真实订单明细仍有按任务当前奖励展示的路径，若真实任务历史改价，不能将该列表奖励直接当作历史结算金额；结算记录才是对应结算的依据。

## 5. Mock 的具体增长规则

### 基准与更新

| 项目 | 当前设定 |
| --- | --- |
| 开始时间 | 2026 年 7 月 29 日 12:00，北京时间 |
| 订单基准 | 2026 年 9 月 12 日 12:00，约 170 万条基础生成订单 |
| Agent 基准 | 同一时点约 3 万，为独立增长指标 |
| 金额 | 最终概览按记录汇总，不强制凑成 1,000 万元 |
| 服务端快照 | 每天生成一次，固定结算上一完整自然日，日内读取同一份快照 |
| Dashboard 查询 | 首次进入时查询，并在北京时间次日 00:00:01 更新一次；隐藏页面不持续后台轮询 |
| 重启后 | 固定任务集合不再增加；按当前时间推导已有执行状态，加载保存的操作状态 |

**170 万是生成部分自身的基准，页面还要加真实订单，不是补齐到总共 170 万。** 任务发布现已停止。即使没人访问，已有执行仍按时间推进，自动订单只在现有任务容量内增长，Agent 指标仍继续增长；停服后启动会计算到当前时刻。

### 订单、发布、执行和 Agent 不是四套无关数字

1. **订单**原增长曲线的长期指数为 1.12，叠加每日、每 10 分钟、每 30 分钟的周期波动；现在增加现有任务分组容量上限，基础自动执行最多 1,716,082 条。真实订单及显式模拟接单不包含在这个基础上限内。
2. **任务**由基础订单分组：每 6 个任务依次分配 9、27、14、32、18、20 条基础执行，合计 120 条。
3. **发布时间**在该任务第一条基础执行之前约 100～140 分钟，最早不早于试运营开始。自动发布截止于 2026 年 9 月 12 日 18:44:05（北京时间），基础任务固定 85,804 个；删除、下线和重新发布等操作仍按原逻辑生效。
4. **执行状态**按接取、提交、验收时间推进，因此执行中和待验收数量可以增加，也可以减少。
5. **Agent 总数**用另一条指数为 0.9 的曲线，叠加每 3 天和每小时波动。没有根据实际注册或订单量反算。

固定 ID 经哈希计算得到不同字段，所以同一用户、订单不会因为刷新换一套资料。这里的波动是规则周期，不是实测的工作日、周末或营销活动影响。

### 重启、改规则和真实任务的区别

- 生成规则不变：相同 ID 的任务内容和时间线稳定，重启不会重新随机，也不会丢失以前的增长。
- 修改生成规则：重新计算时，历史生成任务的名称、说明或附件可能改变。它们没有逐条固化为数据库历史记录；本次任务内容调整即属于这种情况。
- 人工操作：保存在 `MOCK_STATE_PATH` 指定文件，未配置时为 `mock/.data/state.json`。部署必须保留同一文件，不能用空文件覆盖。
- 真实任务：从真实接口读取，不会被生成任务覆盖。管理端仍按发布时间合并排序，旧真实任务可能在后面的分页；停止自动发布后不会再不断被新生成任务挤后。
- 停止发布后，待执行任务逐步完成，验收队列和行为事件可能减少；经过观察窗口后，生成访问统计也可能趋于零。Agent 总量仍独立增长，这是尚未统一的展示口径。

### 执行时间及结果

| 分类 | 基础执行时长 |
| --- | --- |
| 数据处理 | 5～25 分钟 |
| 内容运营 | 15～60 分钟 |
| 商务办公 | 10～45 分钟 |
| 人力资源 | 20～60 分钟 |
| 市场研究 | 45～180 分钟 |
| 金融资讯 | 30～120 分钟 |
| 软件开发 | 30～180 分钟 |
| 设计创意 | 30～120 分钟 |

约 10% 的基础执行额外增加 15～60 分钟，再加入不足 59 秒的差异；提交后等待 5～120 分钟进入最终结果。

基础结果中，每第 55 条执行默认终止，每第 825 条进入申诉规则，约四分之一的生成申诉通过。管理员处理可以覆盖默认结果。

本地 C 端手动接取的 Mock 任务到时间进入待平台验收，之后由管理端处理，不直接按基础订单的定时验收结果完成。

## 6. 业务字段如何生成、如何关联

| 字段 | 生成来源 | 稳定性/限制 |
| --- | --- | --- |
| 任务名、描述、交付要求、验收标准 | 按 12 类场景成套生成，如报价小计核对、反馈标注、英文状态提示、页面状态设计 | 同一任务稳定，但场景组合有限，大量记录中仍会重复 |
| 分类 | 场景对应的数据处理、研发、运营等分类 | 影响执行时长 |
| 奖励 | 大部分约 1～10 元，少量更高，固定 ID 决定 | 尚未充分绑定工作量和后端报价模型 |
| 总名额 | 基础分组数量与生成的 10～50 个名额取较大值 | 管理员可修改；接单扣减剩余名额 |
| 用户昵称 | `用户＋手机号后四位` | 并非每个用户昵称唯一 |
| 手机号 | 不同号段与尾号分别打散计算，中间为星号 | 不来自真实手机号库；真实数据只脱敏，不生成替代值 |
| Agent 类型 | Codex、Claude、OpenCode、Hermes | 当前基础分配较简单，不是按真实市场占比 |
| 执行用户 | 基础执行映射到固定约 3 万的资料池 | 不等同于注册用户库，Agent 总数继续增长也不扩展这个池 |
| 分数、进度、验收摘要 | 按规则和时间生成 | 不是实际测评；C 端模拟执行分数固定为 92 |
| Token 用量、提交时间和说明 | Token 按执行 ID 稳定生成；提交时间取关联执行的 submittedAt；说明来自关联任务 | 未提交的执行不生成交付结果，Token 不是模型实际计费记录 |
| 交付附件 | 任务场景中的交付条目生成 Markdown、CSV，设计类另生成 SVG | 按请求生成；文件可下载但不是实际 Agent 产物；不假装提供不存在的 PPTX 或 Excel 文件 |
| 结算 | 每个完成执行对应一条结算 | 明细和汇总共用规则 |
| 自动打款 | 对应执行结算的实际入账金额 | 当前直接记成功，没有真实调用支付 |

关联链条为：**任务 → 执行订单 → 用户与 Agent → 验收/申诉 → 结算 → 自动打款**。

展示编号会转换成 TK、EX、ST 等形式；接口、路由和行标识保留内部 ID，避免把生成操作发给真实后端。

## 7. 与真实数据如何融合

### 读取和排序

- 两套数据分别读取，汇总指标分别计算后相加。
- 管理端列表按业务时间排序后合并，真实记录不会被替换为生成记录，但也没有强制始终排在最前面。
- 任务按发布时间，验收按提交时间，申诉按提交时间，结算按生成时间，提现按申请时间。
- Mock 普通明细每页 20 条，深分页只取必要的边界与当前页；不把百万条完整对象传给浏览器。
- C 端本地列表采用真实可接任务在前、Mock 可接任务在后的方式，不是管理端的时间归并方式。

### 写入和保存

- 真实 ID 走原后端接口，保留原有审核、结算和支付宝自动打款调用。
- Mock ID 走独立服务，保存编辑、下线、审核等状态和操作日志。
- 状态默认保存在 `apps/sprix-admin/mock/.data/state.json`，也可以配置外部目录；不进入真实数据库。
- 用户在真实 C 端接任务，后台仍能通过真实接口刷新看到。现有更新是轮询，不是业务事件即时推送。
- 真实后端或 Mock 接口失败时，部分页面会显示整体错误；尚未实现两套数据独立降级展示。

### 最近的性能优化

- 相同时间档与操作状态先命中缓存，再决定是否生成快照。
- 事件对象按天缓存并复用，仍按当前时间过滤，不提前显示未来事件。
- 历史任务和未变化的资金汇总行复用，状态或相关金额变化时更新。
- 文件只在打开提交详情或下载时生成，不放进全量任务列表。

本地测试曾观察到热缓存下部分列表接口耗时降到毫秒级；这是本机测试，不保证线上所有接口都如此。冷启动仍有首次构造成本，远程真实接口速度也会影响页面。此次没有改变真实审核或自动打款流程。

### 分页不等于全部接口都已分页

Mock 明细已按页返回；部分真实接口仍全量读取后整理。真实订单查询可能需要读取多个任务详情，申诉全文搜索也可能补齐全部真实详情。第一次进入或复杂搜索仍可能较慢。

## 8. 结算、打款和“真实收入”要怎么理解

### 已参考后端对齐的规则

后端依据为 `SprixServer` main 提交 `31beb5b`，不代表线上当前部署版本。

- 最后一个名额接完，任务自动下线。
- 下线、重新发布有对应状态校验，满额任务不能重新发布。
- 重新发布更新发布时间。
- 创建结算时读取任务当时奖励，结算完成后再改价不重算已有结算。
- 服务费按奖励的 10% 计算，实际入账按奖励减服务费计算，两项分别保留两位小数。
- 同一生成执行的结算、自动打款和汇总使用同一金额算法。

Mock 通过价格历史还原创建结算时的奖励；旧状态缺少历史日志时，不能完整恢复所有旧价格。

### 资金有一处必须知道的取整边界

后端 BigDecimal 计算后按两位小数存储，支付客户端使用 HALF_UP。Mock 对齐这个口径：奖励 1.05 元，服务费 0.105 元、实际入账 0.945 元，分别取整为 0.11 元和 0.95 元，合计比奖励多 0.01 元。

因此不能再保证“任务收入＝取整后服务费＋取整后实际入账”每笔都严格相等。当前没有增加尾差平账机制，也没有擅自修改真实后端规则。

“未提现金额＝实际入账合计－累计已提现”仍按差额计算。未申请提现的余额没有提现单，未提现弹窗列表不一定能够直接加总成该指标。

### 这些金额不等于平台赚到的钱

| 页面金额 | 代表什么 | 不代表什么 |
| --- | --- | --- |
| 累计成交金额 | 任务执行奖励规模 | 平台实际收入 |
| 已完成订单金额 | 已入账结算的任务收入合计 | 平台利润或实际收款证明 |
| 平台服务费 | 结算记录上的服务费 | 已核实收款、扣除成本后的净利润 |
| 实际入账 | 执行用户应得的结算金额 | 平台留存收入 |
| 累计已提现 | 真实已提现加生成的自动打款 | 全部都有真实支付凭证 |

当前没有完整实现付款方实收、支付回单、渠道手续费、退款、冲正和财务对账。**展示接近 1,000 万元不能表述为平台真实赚了 1,000 万元。**

## 9. 用户行为分析：字段、来源及真实性

### 事件内容

生成事件包括：浏览任务市场、查看任务详情、点击按钮、发起接取、接取成功、提交交付和操作失败。

关键按钮参考 C 端现有功能：查看详情、确认接单、智能接单、查看执行详情、连接本地 Agent、开始测评、设为当前执行 Agent、查看收益。

| 字段组 | 包含字段 | 来源 |
| --- | --- | --- |
| 事件 | 事件 ID、名称、发生时间、接收时间 | 根据生成执行时间线构造 |
| 用户和会话 | 用户 ID、昵称、匿名 ID、会话 ID | 固定用户资料与生成访问路径 |
| 页面与按钮 | 页面 ID、按钮 ID、按钮名、来源页面 | 预设 C 端功能映射 |
| 业务关联 | 任务 ID、执行 ID、Agent ID、角色 | 关联基础生成订单 |
| 结果 | 成功/失败、错误码、耗时 | 固定规则，非实际接口耗时 |
| 技术字段 | 来源、环境、版本、链路 ID、动作 ID、结构版本 | 生成元数据 |
| 设备和地区 | 设备类型/品牌/型号、系统、浏览器、网络、运营商、国家、省市、屏幕、时区、语言、基站 | 生成资料，不是真实采集 |

部分技术字段只存在接口数据中，当前弹窗未全部展示。

### 统计规则

- 候选访问路径从基础订单中每隔 64 条选取一个，再按规则决定访问深度；它不是实际流量的随机抽样，也不能乘以 64 当作真实全站流量。
- PV 主要计任务市场和任务详情浏览，不包含整个 C 端所有页面。
- UV 对这些浏览事件按用户去重。
- 点击统计为列出的关键按钮，不是全站所有点击。
- 漏斗要求同一用户、任务路径在 24 小时内依次完成，并按用户去重。
- 漏斗终点是 Agent 提交交付，不是验收通过、结算或真实到账。
- 用户画像固定观察近 30 天，不随事件列表筛选同步缩小窗口。

### 用户画像

约 94% 为电脑、6% 为手机；国家固定中国，省份与城市来自匹配的城市表。较多科技城市有更多条目，但没有按真实地域流量建立权重。

同一用户的设备和地域基本固定。手机号、设备型号、运营商、基站都不是新增采集能力，不能据此判断真实用户使用了某设备或身处某地点。

**目前没有接入真实上报：真实点击不会自动进入这套分析；本地模拟接单和管理员操作也没有完整转成分析事件。因此行为漏斗与操作后的业务状态尚未完全联动。**

## 10. C 端实际可用到什么程度

| 场景 | 当前效果 |
| --- | --- |
| 接真实任务 | 原真实后端流程，资格和 Agent 流程保留 |
| 本地查看 Mock 任务 | 支持列表、详情；已下线或零名额任务不出现在可接列表 |
| 本地模拟接单 | 增加独立执行记录，后台可查询，名额扣减 |
| 模拟执行 | 时间推进到待平台验收，没有向实际 Agent 下发工作 |
| 模拟交付 | 管理端可读取关联生成结果并下载附件；不代表向真实 Agent 下发工作，也不表示 C 端已新增同等附件入口 |
| 模拟审核通过 | 更新对应结算及打款状态，不增加真实钱包余额 |
| 模拟执行申诉 | C 端目前不支持提交 |
| 换浏览器访问模拟我的任务 | 按浏览器本地 owner 标识区分，不是完整的跨设备账户同步 |
| 生产 C 端 | 共享 Mock 受开发环境开关限制，默认生产构建不启用 |

只部署管理端不能让生产 C 端自动同步这些 Mock 任务。

## 11. 哪些地方仍不像真实运营平台

| 优先级 | 差距 | 实际影响 |
| --- | --- | --- |
| 高 | 已有生成交付附件，但评分和 Token 仍来自规则 | 文件内容可查看，仍不能提供真实 Agent 执行和计费证据 |
| 高 | Mock 支付完成即成功 | 看不到正常支付延迟、失败、重试或账户问题 |
| 高 | 埋点和画像仍纯生成 | 无法衡量真实用户增长和行为，也不能指导实际运营 |
| 高 | Agent 总数增长与约 3 万固定资料池不一致 | 不能逐条核验新增 Agent |
| 高 | Mock API 没有服务端身份校验 | 前端登录不能保护直接读写接口，不适合直接当生产业务接口公开 |
| 中 | 任务场景组合有限，价格没有紧密对应工作量 | 大量数据重复，小额复杂任务显得不自然 |
| 中 | 结果比例和周期过于固定 | 每 55 条终止、每 825 条申诉等规则具有机械性 |
| 中 | 基础历史没有完整的上架下架事件重放 | 满额状态已对齐，但每次历史执行的可接资格未完整验证 |
| 中 | 多接口不是同一全局事务快照 | 跨刷新时点可能短暂相差几条或少量金额 |
| 中 | 真实订单奖励展示与历史结算价可能不同 | 改价后需要以结算记录为准，不能用任务当前价格反推全部历史收入 |
| 中 | 真实后端部分接口仍全量读取 | 首次加载、复杂搜索或订单明细可能较慢 |
| 低 | 自动查询触发刷新按钮 loading | 页面有数据却反复转圈；已定位但仍未修改 |

独立 JSON 状态文件目前适合单进程展示服务，不具备成熟业务数据库的多实例并发写入和完整审计能力。

## 12. 建议下一步做什么

1. **完善真实证据链**：目前已让生成任务要求与生成附件对应，后续需要实际执行日志、真实文件来源及质量结果，才能作为真实工作证据。
2. **接入真实行为采集**：将真实 PV、点击和业务事件单独接入，再决定如何与展示数据区分，不能直接把生成分析当真实分析。
3. **让 Agent 总量有明细依据**：按实体记录统计，并明确注册、在线、活跃 Agent 各自口径。
4. **完善支付展示与对账**：按已知后端状态展示，不再让所有生成支付都瞬间成功；明确分位尾差。
5. **补性能与部署边界**：修复 loading 误导，继续完善真实接口分页和 Mock 服务访问保护。

如果目的只是演示业务流程，当前版本已能覆盖主要页面和联动。如果目的是展示平台真实经营成果，应只使用可核验的真实记录，并明确指标口径。

## 14. 更新到服务器时需要做什么

1. 前端页面代码有变更时，重新构建并更新管理端静态文件。
2. 更新 Mock 目录里的服务代码；只替换文件不会让正在运行的 Node 自动加载新模块，需要重启该服务。
3. 保持 `MOCK_STATE_PATH` 指向原持久化文件，保留已有模拟接单和审核状态。
4. 确认反向代理 `/mock-api/` 指向更新后的进程，刷新页面检查任务标题、验收附件与固定任务数量。

85,804 是基础生成任务集合数量，不是页面必须显示的最终总数：真实任务会加进来，删除等操作也会影响可见数量。本文反映当前源码，不保证线上部署版本已一致。
