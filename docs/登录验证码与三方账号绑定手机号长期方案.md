# 登录验证码与三方账号绑定手机号长期设计

版本：v1.0  
日期：2026-06-29  
适用范围：C 端登录弹窗、手机号验证码登录、支付宝扫码登录、微信扫码登录、账号体系、短信验证码、安全验证码、第三方身份绑定

## 1. 设计结论

项目当前还没有正式上线，因此不需要保留临时兼容路径。长期设计直接采用一套干净的账号模型和登录状态机：

1. **手机号是 C 端主账号凭证**。C 端用户必须拥有一个已验证手机号，才能获得正式登录 token。
2. **支付宝、微信是身份提供方，不是主账号**。扫码只证明第三方身份，不能绕过手机号绑定。
3. **第三方扫码成功但未绑定手机号时，不发正式 token**。后端返回 `PHONE_BIND_REQUIRED` 和短期 `bindTicket`，前端继续在登录弹窗内完成手机号绑定。
4. **不再使用 `"未绑定"` 作为手机号占位**。未知手机号统一使用 `phone = null` 和 `phoneVerified = false` 表达。
5. **短信发送前必须完成服务端 safety challenge**。前端本地加减法验证码移除，改成后端生成、后端校验、一次性使用的字母图片验证码。
6. **手机号登录和第三方绑定手机号复用同一套 challenge 能力**。不要为不同入口做两套安全验证。

## 2. 目标与非目标

### 2.1 目标

- 登录体验稳定：用户扫码成功后如果还缺手机号，看到的是自然的“继续绑定手机号”，不是登录失败。
- 账号事实清晰：`phone` 字段只保存真实手机号，`phoneVerified` 表示手机号是否已验证。
- 安全边界清晰：只有完成手机号短信验证后，后端才发正式 token。
- 后端可维护：验证码、短信码、第三方绑定票据各自有独立表和明确生命周期。
- 前端可维护：登录弹窗只维护少量状态，不引入半登录态。

### 2.2 非目标

- 不接入第三方滑块或无感风控作为第一版。接口预留 `challengeType`，后续可替换。
- 不支持第三方扫码后先进入平台再补手机号。这样会产生半登录态和权限分叉。
- 不长期兼容无 challenge 的短信发送接口。项目未上线，应直接改成必填。
- 不把支付宝/微信返回的手机号当成已验证主手机号。主手机号必须通过 Sprix 自己的短信验证码验证。

## 3. 账号模型

### 3.1 主账号表 `user_accounts`

`user_accounts` 表代表 Sprix 内部用户。手机号相关字段应表达真实状态：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `id` | UUID | 用户主键 |
| `nickname` | string | 可来自手机号尾号或第三方昵称 |
| `email` | string | 当前内部占位邮箱可继续保留 |
| `phone` | string nullable | 只有真实手机号才写入，未知为 `null` |
| `phone_verified` | boolean | 默认 `false`，短信验证通过后为 `true` |
| `wechat_open_id` | string nullable | 可作为冗余索引保留，权威绑定关系以 `user_identities` 为准 |
| `wechat_union_id` | string nullable | 可作为冗余索引保留，权威绑定关系以 `user_identities` 为准 |
| 其它业务字段 | existing | 不因登录改造改变语义 |

长期约束：

- `phone` 可以为空。
- `phone` 有值时必须是合法手机号格式。
- `phoneVerified = true` 时 `phone` 必须有值。
- 不允许写入 `"未绑定"`、`"-"`、空字符串作为手机号事实。

### 3.2 身份表 `user_identities`

`user_identities` 表保存外部身份和内部账号的绑定关系。

| 字段 | 规则 |
| --- | --- |
| `user_id` | 绑定的 Sprix 用户 |
| `provider` | `PHONE`、`ALIPAY`、`WECHAT` |
| `provider_user_id` | `PHONE` 用手机号；`ALIPAY` 用支付宝 userId；`WECHAT` 用 openId |
| `union_id` | 微信 unionId，可空 |
| `phone` | 第三方资料携带的手机号或 PHONE identity 的手机号，可空 |
| `display_name` | 第三方昵称，可空 |
| `verified_name` | 支付宝实名信息，可空 |
| `status` | `BOUND` |
| `bound_at` | 绑定时间 |
| `verified_at` | 对该 identity 完成可信验证的时间 |

唯一约束：

- `(provider, provider_user_id)` 唯一。
- 微信如果有 `union_id`，应保证同一 `union_id` 不绑定到多个用户。
- `PHONE` identity 的 `provider_user_id` 即手机号，同一个手机号只能绑定一个用户。

### 3.3 账号合并规则

绑定手机号时按以下顺序处理：

1. 查 `PHONE` identity，若手机号已有账号，使用该账号。
2. 若没有 `PHONE` identity，但 `user_accounts.phone = mobile` 且 `phoneVerified = true`，补建 `PHONE` identity 并使用该账号。
3. 若手机号不存在，创建新 C 端账号，写入 `phone`、`phoneVerified = true`，并创建 `PHONE` identity。
4. 检查支付宝/微信 identity 是否已绑定其它账号；如果已绑定其它账号，拒绝并返回账号冲突。
5. 将支付宝/微信 identity 绑定到手机号账号。
6. 发放正式登录 token。

冲突规则：

- 同一个支付宝 userId 不能绑定多个 Sprix 用户。
- 同一个微信 openId/unionId 不能绑定多个 Sprix 用户。
- 同一个手机号不能绑定多个 Sprix 用户。
- 不自动合并两个都已有业务数据的账号；这种情况应返回明确错误，后续由人工客服处理。

## 4. 服务端安全验证码

### 4.1 设计选择

第一版采用 **后端生成的字母数字图片验证码**：

- 后端生成答案。
- 后端只保存答案 hash，不保存明文答案。
- 后端渲染为 `imageBase64` 返回给前端。
- 前端展示图片，用户输入字符。
- 发送短信时提交 `challengeId + challengeAnswer`。
- 后端校验成功后立即消费 challenge。

这比前端本地加减法稳定，也能阻止直接绕过前端刷短信接口。接口保留 `challengeType`，以后可以替换为第三方滑块或无感风控。

### 4.2 Challenge 场景

| scene | 用途 |
| --- | --- |
| `SMS_LOGIN` | 手机号验证码登录发送短信 |
| `PHONE_BIND` | 支付宝/微信绑定手机号发送短信 |
| `PHONE_CHANGE` | 后续更换手机号发送短信，第一版可不实现 |

### 4.3 表设计 `auth_safety_challenges`

| 字段 | 规则 |
| --- | --- |
| `id` | UUID 或不可猜测随机 id |
| `scene` | `SMS_LOGIN`、`PHONE_BIND`、`PHONE_CHANGE` |
| `challenge_type` | 第一版为 `IMAGE_ALPHANUMERIC` |
| `answer_hash` | `SHA-256(challengeId + ":" + normalizedAnswer + ":" + serverSecret)` |
| `status` | `PENDING`、`USED`、`EXPIRED` |
| `expires_at` | 建议 2 分钟 |
| `used_at` | 消费时间 |
| `ip` | 请求 IP |
| `user_agent` | 浏览器 UA |
| `failure_count` | 错误次数 |

校验规则：

- 答案大小写不敏感。
- 答案只允许字母数字。
- 过期不可用。
- 成功校验后立即标记 `USED`。
- 错误超过 5 次标记 `EXPIRED`，要求重新获取。
- challenge 的 `scene` 必须和短信发送场景一致。

### 4.4 接口

创建验证码：

```text
POST /api/v1/auth/safety-challenges
```

请求：

```json
{
  "scene": "SMS_LOGIN"
}
```

响应：

```json
{
  "challengeId": "uuid",
  "challengeType": "IMAGE_ALPHANUMERIC",
  "imageBase64": "data:image/png;base64,...",
  "expiresInSeconds": 120
}
```

刷新验证码不需要单独接口，前端重新调用创建接口即可。

## 5. 短信验证码

### 5.1 表设计 `sms_verification_codes`

现有短信验证码表可以继续使用，但需要支持多个 scene：

| 字段 | 规则 |
| --- | --- |
| `mobile` | 手机号 |
| `scene` | `LOGIN`、`PHONE_BIND`、`PHONE_CHANGE` |
| `code_hash` | 短信码 hash |
| `status` | `PENDING`、`VERIFIED`、`EXPIRED` |
| `sent_at` | 发送时间 |
| `expires_at` | 建议 10 到 15 分钟 |
| `verified_at` | 验证时间 |

### 5.2 手机号登录发送短信

```text
POST /api/v1/auth/sms-codes
```

请求：

```json
{
  "mobile": "13812345678",
  "scene": "LOGIN",
  "challengeId": "uuid",
  "challengeAnswer": "K7QH"
}
```

响应：

```json
{
  "mobile": "13812345678",
  "expiresInSeconds": 900,
  "resendIntervalSeconds": 60
}
```

规则：

- `scene` 第一版只允许 `LOGIN`。
- `challengeId` 和 `challengeAnswer` 必填。
- challenge 必须是 `SMS_LOGIN` 场景。
- challenge 通过后才发送短信。
- 保留单手机号重发间隔。
- 保留单手机号、单 IP 的发送频控。

### 5.3 手机号登录确认

```text
POST /api/v1/auth/sms-login
```

请求：

```json
{
  "mobile": "13812345678",
  "code": "123456"
}
```

响应：

```json
{
  "userId": "uuid",
  "nickname": "用户5678",
  "role": "CONSUMER",
  "token": "satoken_xxx"
}
```

规则：

- 短信码只能使用一次。
- 验证成功后创建或复用手机号账号。
- 写入 `phoneVerified = true`。
- 确保存在 `PHONE` identity。

## 6. 第三方扫码登录与手机号绑定

### 6.1 总体状态流

```text
创建扫码 session
  -> PENDING
用户扫码授权
  -> 后端拿到 provider identity
  -> 如果 identity 已绑定到 phoneVerified 用户
       -> CONFIRMED，轮询接口返回 token
  -> 如果 identity 未绑定
       -> PHONE_BIND_REQUIRED，轮询接口返回 bindTicket
前端展示手机号绑定表单
  -> 获取 PHONE_BIND safety challenge
  -> 发送 PHONE_BIND 短信
  -> 确认短信码
  -> 绑定 identity 到手机号账号
  -> 返回 token
```

### 6.2 扫码 session 状态

支付宝和微信状态统一使用：

| status | 含义 |
| --- | --- |
| `PENDING` | 等待扫码授权 |
| `CONFIRMED` | 已确认，且可直接登录 |
| `PHONE_BIND_REQUIRED` | 第三方身份已确认，但需要绑定手机号 |
| `EXPIRED` | session 过期 |
| `ERROR` | 第三方回调或账号冲突异常 |

### 6.3 扫码状态响应

支付宝：

```text
GET /api/v1/auth/alipay/login-sessions/{sessionId}
```

微信：

```text
GET /api/v1/auth/wechat/scan-sessions/{sessionId}
```

响应统一结构：

```json
{
  "sessionId": "uuid",
  "status": "PHONE_BIND_REQUIRED",
  "expiresInSeconds": 240,
  "authenticated": false,
  "phoneBindRequired": true,
  "provider": "ALIPAY",
  "bindTicket": "ticket_xxx",
  "token": null
}
```

如果可以直接登录：

```json
{
  "sessionId": "uuid",
  "status": "CONFIRMED",
  "expiresInSeconds": 240,
  "authenticated": true,
  "phoneBindRequired": false,
  "provider": "ALIPAY",
  "bindTicket": null,
  "token": {
    "userId": "uuid",
    "nickname": "用户5678",
    "role": "CONSUMER",
    "token": "satoken_xxx"
  }
}
```

### 6.4 Bind ticket 表 `auth_phone_bind_tickets`

| 字段 | 规则 |
| --- | --- |
| `id` | 不可猜测 ticket |
| `provider` | `ALIPAY` 或 `WECHAT` |
| `provider_user_id` | 支付宝 userId 或微信 openId |
| `union_id` | 微信 unionId，可空 |
| `display_name` | 第三方昵称，可空 |
| `verified_name` | 支付宝实名，可空 |
| `raw_phone` | 第三方资料手机号，可空，不作为已验证手机号 |
| `session_id` | 来源扫码 session |
| `status` | `PENDING`、`BOUND`、`EXPIRED` |
| `expires_at` | 建议 10 分钟 |
| `bound_user_id` | 完成绑定后的用户 id |

规则：

- ticket 只能使用一次。
- ticket 过期后必须重新扫码。
- ticket 不等于登录态，不能访问业务接口。
- ticket 只允许完成绑定手机号相关接口。

### 6.5 发送绑定手机号短信

```text
POST /api/v1/auth/phone-bind/sms-codes
```

请求：

```json
{
  "bindTicket": "ticket_xxx",
  "mobile": "13812345678",
  "challengeId": "uuid",
  "challengeAnswer": "K7QH"
}
```

响应：

```json
{
  "mobile": "13812345678",
  "expiresInSeconds": 900,
  "resendIntervalSeconds": 60
}
```

规则：

- `bindTicket` 必须有效且未过期。
- challenge 必须是 `PHONE_BIND` 场景。
- 短信验证码写入 `scene = PHONE_BIND`。
- 发送频控与登录短信共用底层策略。

### 6.6 确认绑定手机号

```text
POST /api/v1/auth/phone-bind/confirm
```

请求：

```json
{
  "bindTicket": "ticket_xxx",
  "mobile": "13812345678",
  "code": "123456"
}
```

响应：

```json
{
  "userId": "uuid",
  "nickname": "用户5678",
  "role": "CONSUMER",
  "token": "satoken_xxx"
}
```

规则：

- 校验 `PHONE_BIND` 短信码。
- 创建或复用手机号主账号。
- 绑定支付宝/微信 identity。
- 标记 ticket 为 `BOUND`。
- 返回正式 token。

## 7. 前端设计

### 7.1 登录弹窗结构

保留三个入口：

- 支付宝扫码登录
- 微信扫码登录
- 手机号验证码登录

手机号登录和第三方绑定手机号共用验证码能力，但 UI 不需要暴露复杂概念。

### 7.2 手机号验证码登录状态

```text
idle
  -> loadingChallenge
  -> challengeReady
  -> sendingSms
  -> smsSent
  -> submitting
  -> authenticated
```

交互：

1. 用户输入手机号，点击“获取验证码”。
2. 前端调用 `createSafetyChallenge("SMS_LOGIN")`。
3. 弹出安全验证，展示图片验证码。
4. 用户输入图片验证码，点击“发送验证码”。
5. 前端调用 `sendSmsCode({ mobile, scene: "LOGIN", challengeId, challengeAnswer })`。
6. 发送成功后进入倒计时。
7. 用户输入短信验证码并登录。

### 7.3 第三方扫码登录状态

```text
qrLoading
  -> qrPending
  -> qrConfirmedWithToken
  -> phoneBindRequired
  -> phoneBindChallengeReady
  -> phoneBindSmsSent
  -> authenticated
```

第三方扫码返回 `PHONE_BIND_REQUIRED` 时，登录弹窗不关闭，切换为绑定手机号面板：

```text
支付宝验证成功
为了保障账号安全，请绑定手机号

[手机号]
[短信验证码] [获取验证码]
[完成绑定并登录]
```

点击“获取验证码”时同样先弹出图片验证码。

### 7.4 前端服务封装

建议封装为明确的 auth API：

```ts
createSafetyChallenge(scene: "SMS_LOGIN" | "PHONE_BIND")
sendSmsCode(input: { mobile: string; scene: "LOGIN"; challengeId: string; challengeAnswer: string })
authenticateConsumer(mobile: string, code: string)
createAlipayLoginSession()
readAlipayLoginStatus(sessionId: string)
createWechatLoginSession()
readWechatLoginStatus(sessionId: string)
sendPhoneBindSmsCode(input: { bindTicket: string; mobile: string; challengeId: string; challengeAnswer: string })
confirmPhoneBind(input: { bindTicket: string; mobile: string; code: string })
```

### 7.5 前端账号映射

`mapAccount` 应按以下规则计算：

- `phone = account.phone ?? ""`
- `phoneVerified = account.phoneVerified === true`
- `maskedPhone = phoneVerified ? maskPhone(account.phone) : ""`
- 没有已验证手机号时，页面显示“未绑定手机号”，但不把该文案写回数据层。

## 8. 错误处理

后端错误码建议：

| code | 使用场景 |
| --- | --- |
| `SAFETY_CHALLENGE_REQUIRED` | 未提交 challenge |
| `SAFETY_CHALLENGE_INVALID` | challenge 错误、过期、重复使用 |
| `SMS_CODE_INVALID` | 短信码错误或过期 |
| `PHONE_BIND_REQUIRED` | 第三方身份需要绑定手机号 |
| `PHONE_BIND_TICKET_INVALID` | ticket 错误、过期、已使用 |
| `IDENTITY_ALREADY_BOUND` | 第三方身份已绑定其它账号 |
| `PHONE_ALREADY_BOUND_CONFLICT` | 手机号绑定冲突 |

前端文案：

- 图片验证码错误：`验证码不正确，请重新输入`
- 图片验证码过期：`验证码已过期，请重新获取`
- 短信码错误：`短信验证码不正确或已过期`
- ticket 过期：`绑定状态已过期，请重新扫码`
- 身份冲突：`该账号已绑定其他手机号，请联系客服处理`

## 9. 实施顺序

因为项目未上线，推荐一次性按长期模型实施，但代码提交可以拆成可验证的阶段：

### 阶段一：账号模型打干净

1. `user_accounts.phone` 改为 nullable。
2. 新增 `user_accounts.phone_verified`。
3. 清理所有 `"未绑定"` 写入逻辑。
4. `IdentityService` 创建支付宝/微信账号时不再创建无手机号主账号，改为进入绑定流程。
5. `mapAccount` 改为读取 `phoneVerified`。

验收：

- 数据库不再出现 `phone = "未绑定"`。
- 未绑定手机号的账号不会被视作手机号已验证。
- 手机号登录用户一定有 `PHONE` identity。

### 阶段二：服务端 safety challenge

1. 新增 `auth_safety_challenges`。
2. 新增 `POST /api/v1/auth/safety-challenges`。
3. 修改 `/api/v1/auth/sms-codes`，要求 challenge 必填且场景正确。
4. 删除前端本地加减法校验。
5. 前端展示服务端图片验证码。

验收：

- 没有 challenge 不能发送短信。
- challenge 错误、过期、重复使用都不能发送短信。
- 正确输入字母验证码后可以发送短信。
- 字母大小写不敏感。

### 阶段三：第三方扫码绑定手机号

1. 新增 `auth_phone_bind_tickets`。
2. 支付宝/微信扫码确认后，如果 identity 未绑定已验证手机号账号，返回 `PHONE_BIND_REQUIRED`。
3. 新增绑定手机号短信发送接口。
4. 新增绑定手机号确认接口。
5. 前端登录弹窗增加 `PhoneBindPanel`。

验收：

- 新支付宝/微信用户扫码后不能直接进入平台，必须绑定手机号。
- 绑定手机号成功后才获得 token。
- 已绑定过的支付宝/微信用户扫码后可直接登录。
- 第三方身份绑定已有手机号时合并到原手机号账号。
- 同一个第三方身份不能绑定多个账号。

### 阶段四：回归与清理

1. 删除前端本地验证码生成逻辑。
2. 删除后端 `"未绑定"` 兼容判断。
3. 删除无 challenge 的短信发送路径。
4. 补齐后端和前端测试。

## 11. 关键风险

1. **数据库迁移风险**：`phone` 当前是非空字段，改 nullable 需要迁移脚本和实体同步。
2. **账号合并风险**：手机号账号和第三方身份都有业务数据时不能盲目合并，第一版应返回冲突。
3. **短信成本风险**：challenge 只能降低刷短信风险，还需要短信接口自身的手机号/IP 频控。
4. **第三方资料不稳定**：支付宝/微信返回手机号不一定稳定或可用，不能作为 Sprix 主手机号。
5. **前端状态复杂度**：不要引入临时 token，否则登录弹窗、全局鉴权、页面权限都会变复杂。

## 12. 明确不采用

- 不采用前端本地加减法验证码。
- 不采用前端本地字母验证码。
- 不采用扫码成功后直接创建 `phone = "未绑定"` 的账号。
- 不采用第三方扫码后发临时 token 再补手机号。
- 不采用独立绑定手机号页面作为第一版主流程。
- 不长期保留未提交 challenge 也能发送短信的接口。
