# C 端申诉通道前后端改动清单

## 背景

产品交互要求：验收未通过的任务支持用户提交一次申诉。申诉入口需要同时出现在：

- C 端「我的任务」列表中，任务状态为「验收未通过」且未申诉时，操作区展示「申诉 / 重新执行」。
- C 端任务执行详情页顶部任务概览卡中，当前 execution 状态为「验收未通过」且未申诉时，展示「申诉 / 重新执行」。

当前结论：

- 后端已有申诉提交、后台审核通过、后台审核不通过的核心接口和状态流转。
- C 端「我的任务」列表已有申诉入口。
- C 端任务详情页还缺申诉入口。
- C 端申诉提交成功文案与产品文案不一致。
- 如果产品需要 C 端查看申诉详情或处理结果说明，当前还需要补一个 C 端只读查询能力。

## 产品要求对照

| 产品要求 | 当前实现 | 需要调整 |
| --- | --- | --- |
| 验收未通过且未申诉时展示「申诉 / 重新执行」 | 我的任务列表已实现 | 任务详情页也要补齐 |
| 「申诉」按钮位于「重新执行」左侧 | 我的任务列表已符合 | 详情页保持同样顺序 |
| 提交申诉弹窗包含申诉理由 | 已有 `AppealModal` | 保留 |
| 提交成功后进入「申诉处理中」 | 后端会把 execution `appealStatus` 更新为 `PENDING` | 前端需确保列表和详情刷新后显示处理中 |
| 提交成功提示「申诉已提交，平台将在 1-3 个工作日内返回处理结果」 | 当前提示为「申诉已提交，处理进度以后端返回状态为准」 | 调整文案 |
| 申诉处理中、申诉通过、申诉不通过状态下按钮禁用 | 我的任务列表已有规则 | 详情页复用同一规则 |
| C 端不提供补充材料入口 | 当前没有补充材料入口 | 保持不做 |

## 前端改动

### 1. 任务详情页补申诉入口

涉及文件：

- `apps/sprix-agent/src/user/UserPages.tsx`
- `apps/sprix-agent/src/App.tsx`

需要做：

- `MyTaskDetailPage` 接收 `openAppeal` 回调。
- 路由渲染任务详情页时，把全局 `openAppeal(executionId)` 传进去。
- 在详情页顶部任务概览区域，根据当前 execution 状态展示操作按钮。
- 复用现有 `getMyTaskActions(task)` 判断逻辑，避免列表页和详情页状态不一致。
- 按钮顺序保持为「申诉 / 重新执行」。

验收行为：

- 任务为「验收未通过」且 `appealStatus = NOT_APPEALED` 时，详情页展示可点击「申诉」和「重新执行」。
- 任务为「申诉处理中 / 申诉通过 / 申诉不通过」时，详情页展示对应禁用态，不允许重复提交。

### 2. 详情页复用重新执行逻辑

涉及文件：

- `apps/sprix-agent/src/user/UserPages.tsx`

需要做：

- 当前重新执行逻辑主要在我的任务列表页使用。
- 详情页也需要调用同一个 `rerunRemoteTask(executionId)` 能力。
- 成功后刷新 `["sprix-agent"]` 查询，保证列表、详情、统计同步更新。

验收行为：

- 详情页点击「重新执行」后，接口成功返回时刷新当前数据。
- 重新执行失败时展示后端错误信息。

### 3. 调整申诉弹窗文案

涉及文件：

- `apps/sprix-agent/src/components/GlobalModals.tsx`

需要做：

- 成功提示改为：`申诉已提交，平台将在 1-3 个工作日内返回处理结果`。
- 弹窗说明保持产品语义：用户认为验收结果存在误判时提交申诉，平台在 1-3 个工作日处理。

验收行为：

- 提交成功后用户看到与产品一致的提示。

### 4. 可选：C 端申诉详情查看

当前产品 prompt 主要要求提交和状态展示，没有明确要求 C 端查看申诉详情。

如果后续产品要求用户能查看申诉原因、平台处理结果或驳回原因，需要新增：

- C 端「查看申诉」入口。
- 只读申诉详情弹窗或详情区。
- 后端提供 C 端按 execution 查询申诉记录的接口，或在任务详情接口中返回申诉快照。

## 后端改动

### 已有能力

后端当前已有：

- `POST /api/v1/appeals`：C 端提交申诉。
- 只允许当前用户对自己的 execution 提交申诉。
- 只允许 `ACCEPTANCE_FAILED` 的 execution 提交申诉。
- 只允许 `NOT_APPEALED` 状态提交一次申诉。
- 提交后创建 `AppealRecord`，并把 execution `appealStatus` 更新为 `PENDING`。
- 后台审核通过后，把 appeal 状态更新为 `APPROVED`，并进入结算流程。
- 后台审核不通过后，把 appeal 状态更新为 `REJECTED`。

### 需要确认或补充

1. 确认 C 端我的任务列表接口返回 `appealStatus`

   前端列表和详情都需要依赖它判断按钮状态。至少需要返回：

   - `NOT_APPEALED`
   - `PENDING`
   - `PROCESSING`
   - `APPROVED`
   - `REJECTED`

2. 确认 C 端任务详情接口返回 `appealStatus`

   如果详情页复用列表数据还不够，需要任务详情接口也返回同样字段。

3. 如果要展示申诉详情，补 C 端只读查询接口

   建议接口：

   ```http
   GET /api/v1/appeals/by-execution/{executionId}
   ```

   返回建议包含：

   - `id`
   - `executionId`
   - `status`
   - `reason`
   - `reviewComment`
   - `createdAt`
   - `processedAt`

4. Swagger 同步

   如果新增或调整后端字段、接口，需要重新生成 Swagger，并同步到前端生成 API：

   - `apps/sprix-agent/src/apis/_swaggers/sprix.json`
   - `apps/sprix-agent/src/apis/sprix/api.ts`

## 状态映射建议

| 后端状态 | C 端展示 |
| --- | --- |
| `NOT_APPEALED` | 申诉 |
| `PENDING` | 申诉处理中 |
| `PROCESSING` | 申诉处理中 |
| `NEED_SUPPLEMENT` | 申诉处理中 |
| `APPROVED` | 申诉通过 |
| `REJECTED` | 申诉不通过 |

说明：产品当前明确 C 端不提供补充材料入口，所以 `NEED_SUPPLEMENT` 在 C 端不建议开放额外操作，可先统一展示为「申诉处理中」。

## 验收用例

1. 未通过且未申诉

   - 我的任务列表展示「申诉 / 重新执行」。
   - 任务详情页展示「申诉 / 重新执行」。
   - 点击「申诉」打开提交申诉弹窗。

2. 提交申诉成功

   - 调用 `POST /sprix-api/api/v1/appeals` 成功。
   - Toast 展示「申诉已提交，平台将在 1-3 个工作日内返回处理结果」。
   - 列表和详情刷新后展示「申诉处理中 / 重新执行」。
   - 「申诉处理中」不可点击。

3. 重复提交申诉

   - 前端不再提供可点击入口。
   - 后端拒绝重复提交。

4. 平台审核通过

   - 后台通过后，C 端任务状态和申诉状态刷新。
   - C 端展示「申诉通过」禁用态。
   - 后端进入结算流程。

5. 平台审核不通过

   - 后台不通过后，C 端展示「申诉不通过」禁用态。
   - 用户不能再次申诉。

6. 非验收未通过任务

   - 不展示申诉入口。
   - 不影响原有任务操作。

## 建议实施顺序

1. 先补 C 端任务详情页申诉和重新执行入口。
2. 修正申诉弹窗成功文案。
3. 联调确认 C 端列表和详情数据里都有 `appealStatus`。
4. 如产品确认需要查看申诉详情，再补后端只读查询接口和前端展示。
5. 最后按验收用例走一遍列表、详情、提交、后台审核后的状态刷新。
