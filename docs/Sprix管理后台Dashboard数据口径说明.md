# Sprix 管理后台 Dashboard 数据口径说明

## 1. 文档范围

本文说明管理后台 `/dashboard` 当前可见字段的数据来源、计算公式和模块之间的关系，适用于以下代码：

- 页面入口：`apps/sprix-admin/src/admin/AdminDashboard.tsx`
- 页面模块：`apps/sprix-admin/src/admin/DashboardBusinessMetrics.tsx`
- 订单明细：`apps/sprix-admin/src/admin/DashboardOrders.tsx`
- 接口与类型：`apps/sprix-admin/src/services/dashboardAnalyticsMock.ts`
- Dashboard Mock 接口：`apps/sprix-admin/mock/server.mjs`
- 经营数据生成：`apps/sprix-admin/mock/business-metrics.mjs`
- 平台累计展示模型：`apps/sprix-admin/mock/analytics-data.mjs`
- 订单增长模型：`apps/sprix-admin/mock/business-scenario.mjs`

本次对账采用以下 Excel 优先级：

1. `sprixAI数据看板4.0.xlsx`：周度经营控制数的唯一原始口径。
2. `sprixAI数据看板5.1_待审核待结算版.xlsx`：日拆分、任务管理、验收中心和待结算模块的最新明细口径。
3. 当前 Mock 代码：实现结果，必须向上述 Excel 对齐，不能反过来用代码覆盖 Excel 口径。

5.1 文件内也明确注明“4.0 周度数据为唯一控制数”。因此，周总量发生冲突时以 4.0 为准；4.0 没有提供的日粒度和模块明细，以最新 5.1 为对账基准。

当前 Dashboard 请求：

```text
GET /mock-api/dashboard/analytics?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD
```

默认查询日期为 `2026-07-27` 至 `2026-09-06`。下方按日和近六周经营数据以 Excel 为准，截止 `2026-09-06 23:59:59`；顶部平台累计规模延伸至 `2026-09-13 23:59:59`（北京时间）。

> 重要说明：当前接口是展示用 HTTP Mock。经营周报部分来自代码内固化的六周经营数据；平台累计规模中的订单、任务、Agent 和成交金额在六周 Excel 控制数上增加 9 月 7–13 日的 Mock 延伸周。延伸周复用最近完整周 8 月 31 日–9 月 6 日的规模，不属于 Excel 原始数据。它们不是从线上业务数据库实时聚合得到的真实经营事实。

## 2. 数据结构与推导层级

Dashboard 数据分成四层：

1. **周级原始经营输入**：六周新增 Agent、异构 Agent 比例、验收 GMV、有效 Agent、各类型交付数、分类交付金额、分类质检通过率。
2. **确定性拆分数据**：把周总量按工作日权重拆成每日数据，把任务数量分配到任务主单和名额。
3. **页面汇总指标**：对日数据、周数据和分类数据求和、求比例或计算费用。
4. **平台累计展示模型**：累计订单、累计任务、Agent 和累计成交金额等于六周 Excel 控制数加一个 Mock 延伸周。

因此，页面顶部与下方经营模块不是完全相同的数据源：

| 页面区域 | 主要来源 | 性质 |
| --- | --- | --- |
| 平台累计规模 | `analytics-data.mjs` + `business-metrics.mjs` | 六周 Excel 数据 + 9 月 7–13 日 Mock 延伸周；截至 2026-09-13 |
| 按日经营数据 | `business-metrics.mjs` | 六周经营输入经过确定性日拆分 |
| 近六周经营数据 | `business-metrics.mjs` | 六周固化经营输入及其派生值 |
| 订单抽屉 | `business-metrics.mjs` 生成的执行记录，经 `/mock-api/admin/view` 分页 | 与任务、执行、分类、金额共用同一经营快照 |

| 08.03–08.09 | 1,689 | 22.46% | ¥108,850 | 1,785 | 1,963 |

## 4. 平台累计规模

### 4.1 累计成交金额

页面字段：`overview.amount`。

Dashboard 的初始累计基准使用“发单任务类型 & 交付金额”模块中六周分类交付金额的总和，再增加 9 月 7–13 日 Mock 延伸周金额。延伸周复用最近完整周的 `¥586,700`：

```text
累计成交金额
= 六周分类交付金额 + 延伸周分类交付金额
= ¥1,699,400 + ¥586,700
= ¥2,286,100
```

每周各任务类型的交付金额合计等于该周验收 GMV。下方近六周仍显示 Excel 合计 `¥1,699,400`；顶部以 `¥2,286,100` 为初始值，Mock 服务运行后每 5 分钟按 1–5 次模拟成交对应的随机金额继续累加。这个变化只用于顶部实时感，不生成业务明细，也不是平台收入、提现金额或财务实收。

### 4.2 累计订单

页面字段：`overview.orders`。

Dashboard 的初始累计订单使用六周经营快照中的 Agent 交付任务总量，再增加 9 月 7–13 日 Mock 延伸周交付量。延伸周复用最近完整周的 `4,544` 条：

```text
累计订单 = Agent 交付任务量总数
         = 六周交付数 + 延伸周交付数
         = 16,251 + 4,544
         = 20,795
```

这里统计的是执行/交付条数，不是任务主单数。下方日期范围截止 9 月 6 日，因此仍为 `16,251`；顶部以 `20,795` 为初始值，之后每 5 分钟增加 1–5。该增量只改变顶部计数，不生成订单或执行记录。接口不再使用“45 天约 170 万订单”的历史展示模型。

### 4.3 累计任务数量

页面字段：`overview.tasks`。

当前 Dashboard 使用六周经营快照任务主单数，加上延伸周按最近完整周复用的 `3,029` 个任务主单：

```text
累计任务数量 = 10,834 + 3,029 = 13,863 个任务主单
```

任务主单不是交付订单。一张任务主单可以有多个名额和多条执行订单。

5 分钟的顶部变化不创建任务、不消费任务名额，因此累计任务数量保持 `13,863` 不变。

任务主单数量由各任务类型的固定主单总量相加得到：

```text
9,134 + 37 + 929 + 345 + 45 + 344 = 10,834
```

### 4.4 Agent 数量

页面字段：`overview.agents`。

Dashboard 的初始 Agent 数量使用六周新增 Agent 合计，再加上延伸周按最近完整周复用的 `3,605`：

```text
Agent 数量 = 30,914 + 3,605
           = 34,519
```

Mock 服务运行后，只有 Dashboard 顶部的 Agent 数量每 5 分钟独立增加 1–5；验收中心等具体模块仍读取按周更新的固定数据。

## 5. 按日经营数据

> Excel 边界：4.0 只提供周总量，没有日明细；最新 5.1 提供 42 天的模拟日拆分。当前代码会用另一套固定哈希权重重新拆分，所以虽然每周和六周合计正确，但页面每天的数值并不等于 5.1 Excel。下列公式描述的是当前代码算法，不代表已经与 Excel 日明细对齐。

### 5.1 新增 Agent

页面汇总字段：`businessMetrics.summary.newAgents`。

```text
所选日期新增 Agent = Σ 所选日期内 dailyNewAgents.total
```

每日值不是逐条 Agent 注册记录统计，而是由每周新增总量拆分得到。当前代码拆分使用以下星期权重：

```text
周一至周日权重 = [1.08, 1.16, 0.96, 1.12, 1.02, 0.38, 0.34]
```

每个日期再叠加固定哈希产生的 0.94～1.06 小幅系数，最后通过“先取整、再按小数余量补齐”的方法保证：

```text
Σ 每日新增 Agent = 当周新增 Agent 原始总量
```

### 5.2 每日新增 Agent 图

柱高直接使用当日 `dailyNewAgents.total`。纵轴最大值取当前所选日期内的最大日新增数。

日期筛选后，仅保留日期在 `startDate` 与 `endDate` 之间的数据点。

### 5.3 每日新增 Agent 类型构成

先将每周各 Agent 类型总量按当周每日新增量拆分成“类型 × 日期”矩阵，再计算当日占比：

```text
某类型当日占比 = 该类型当日新增数 / 当日全部新增 Agent 数
```

所有类型当日数量之和等于当日新增 Agent 数，所有占比之和为 100%。页面使用 100% 堆叠面积图展示构成变化。

### 5.4 Agent 交付任务数

页面汇总字段：`businessMetrics.summary.deliveredTasks`。

```text
所选日期交付任务数 = Σ 所选日期内 dailyDelivery.tasks
```

当前代码先把每周任务分类总数按同一星期权重拆到每天，再把所有任务类型的每日值相加。拆分后始终满足：

```text
Σ 每日交付任务数 = Σ 当周各类型交付任务数
```

这里的“交付任务数”实际对应执行/交付条数，不等于任务主单数。

### 5.5 日有效 Agent 数

每日有效 Agent 数由周有效 Agent 数和每日交付任务数推导：

```text
当周日有效 Agent 人次总量
= min(当周交付任务数, ceil(当周有效 Agent × 周重复参与系数))
```

六周重复参与系数依次为：

```text
[1.03, 1.04, 1.02, 1.06, 1.10, 1.08]
```

然后按每日任务量加权拆分，并限制：

```text
某日有效 Agent 数 <= 某日交付任务数
```

因此图中的日有效 Agent 是从周去重人数推导出的日参与人数，不应将七天数值相加后当作周去重 Agent 数。

### 5.6 交付任务类型构成

页面按所选日期汇总每个任务类型的每日交付数：

```text
某类型交付数 = Σ 所选日期内该类型 daily 数量
某类型占比 = 某类型交付数 / 全部类型交付数
```

分类按交付数量降序展示。点击分类后，任务列表携带相同日期范围和分类参数进行筛选。

## 6. 近六周经营数据

### 6.1 近六周验收 GMV

```text
近六周验收 GMV = Σ 六周 acceptedGmv = ¥1,699,400
```

每周验收 GMV来自 `rawWeeks` 的周级输入。页面点击后打开订单抽屉，默认查看已完成订单；但当前经营快照生成的 16,251 条执行初始状态均为“待验收”，因此周报 GMV与订单列表状态并不是由同一批“已完成订单”现场求和得出，而是周报输入值与演示执行状态并列展示。

### 6.2 近六周交付任务数

```text
近六周交付任务数 = Σ 六周 deliveredTasks = 16,251
```

其中每周 `deliveredTasks` 等于该周六个任务类型交付数之和。

### 6.3 最新统计周

最新统计周取 `weeks` 数组最后一周，即 `2026-08-31` 至 `2026-09-06`。

| 字段 | 计算方式 | 当前值 |
| --- | --- | ---: |
| 周验收 GMV | 最新周 `acceptedGmv` | ¥586,700 |
| 有效 Agent | 最新周 `effectiveAgents` | 3,544 |
| 单个有效 Agent 周均 GMV | `586,700 / 3,544` | ¥165.55 |
| 异构 Agent 比例 | 最新周 `heterogeneousRate × 100%` | 12.74% |

“异构 Agent 比例”是周级输入值，代码没有再从 Agent 类型分布反算该比例。

### 6.4 周验收 GMV与同周有效 Agent 图

- 左轴：每周 `acceptedGmv`，显示单位换算为万元。
- 右轴：每周 `effectiveAgents`。
- 两条折线只共享横轴，不做相除或归一化。

### 6.5 周度异构 Agent 比例图

每个点直接使用每周 `heterogeneousRate × 100%`。纵轴上限取 `max(40%, 所有周实际最大比例)`，所以即使实际比例都低于 40%，图表仍保留 0～40% 的基础观察范围。

### 6.6 分类交付金额

每个单元格来自对应周、对应任务类型的 `amount`。每周六个类型的金额满足：

```text
Σ 当周各类型 amount = 当周 acceptedGmv
```

金额表中的“合计”行直接显示每周 `acceptedGmv`，并非浏览器再次对表格单元格求和。

### 6.7 各类型质检通过率

周级输入 `passRate` 同时被解释为自动交付金额占分类验收 GMV 的比例：

```text
质检通过率 = 自动交付金额 / 分类验收 GMV
自动交付金额 = 分类验收 GMV × passRate
人工上传交付金额 = 分类验收 GMV × (1 - passRate)
```

若某分类的 `passRate` 为 `null`，页面不画该周该分类的质检率点，同时该分类自动/人工交付金额均按 0 处理。它表示“没有可用口径”，不表示 0% 通过率。

### 6.8 待结算费用

当前结算比例是代码中的展示规则：

```text
Agent 自动交付待结算 = 自动交付金额 × 10%
人工上传交付待结算 = 人工上传交付金额 × 60%
待结算费用合计 = 上述两项之和
```

六周当前值：

| 字段 | 当前值 |
| --- | ---: |
| Agent 自动交付金额 | ¥620,732.25 |
| Agent 自动交付待结算 | ¥62,073.23 |
| 人工上传交付金额 | ¥1,078,667.75 |
| 人工上传交付待结算 | ¥647,200.65 |
| 待结算费用合计 | ¥709,273.88 |

这些值来自六周分类金额与 `passRate` 的推导，不是从提现、打款或结算流水表求和。

## 7. 任务主单、名额与执行订单的关系

当前经营快照满足：

```text
任务主单数 = 10,834
总名额数 = 18,370
执行/交付数 = 16,251
剩余名额数 = 18,370 - 16,251 = 2,119
```

各任务类型的任务主单总量：

```text
[数据标注 9,134, 网站开发 37, 营销 929, 设计 345, 知识问答 45, 其他 344]
```

各任务类型的总名额：

```text
[数据标注 15,487, 网站开发 62, 营销 1,575, 设计 586, 知识问答 77, 其他 583]
```

生成过程如下：

1. 按每周、每类型的交付数权重，把各类型任务主单总量分配到六周。
2. 把“交付数 - 主单数”按确定性权重追加到各主单，使一张主单可对应多个执行。
3. 把剩余名额分配到各主单。
4. `totalSlots = executionTotal + remainingSlots`。
5. `remainingSlots > 0` 的任务为“已发布”，名额用尽则为“已下线”。

因此，下列数字是截至 9 月 6 日、可与 Excel 和明细列表核对的六周基础数：

- 六周任务主单数为 10,834。
- 六周执行/交付数为 16,251。
- C 端可见任务还必须满足“已发布且剩余名额大于 0”。

顶部累计任务和累计订单的初始值另加一个 Mock 延伸周，分别为 13,863 和 20,795；该延伸周基准尚无对应逐条明细。服务启动后的 5 分钟增量也只属于顶部展示，不进入订单分页、任务详情、验收中心或交付结果查询；这些具体模块统一按周更新。

## 8. 订单抽屉的数据口径

点击“近六周验收 GMV”会打开订单记录抽屉。列表通过分页接口读取经营执行记录，每页 10 条。

字段映射：

| 列 | 来源/计算 |
| --- | --- |
| 执行 ID | `executionId`，由经营执行序号生成 |
| 关联任务 | 执行所属任务主单的标题和 ID |
| 任务分类 | 继承所属任务主单分类 |
| 状态 | `running / reviewing / completed / terminated` |
| Agent 数量 | 平台验收中心按 `agentId` 去重；缺少 ID 时按 `agentName` 去重 |
| 执行用户 | 明细记录中保留执行用户身份，不再作为验收中心顶部汇总指标 |
| 订单奖励 | 该执行分配到的验收金额，保留两位小数 |
| 状态时间 | 执行状态对应时间；当前经营快照主要为提交时间 |

分类交付金额会先按自动/人工交付占比分成整数“分”，再分配给每条执行，所以同一分类下各执行奖励可能不同，但满足：

```text
Σ 某周某分类全部执行奖励 = 该周该分类交付金额
```

订单按状态时间倒序展示；日期范围按状态时间筛选，而不是按任务发布时间筛选。

## 9. 日期筛选的实际影响

日期选择器允许选择 `2026-07-27` 至 `2026-09-06` 内的范围。

会随日期范围重算的字段：

- 新增 Agent 汇总。
- 每日新增 Agent 图。
- 每日新增 Agent 类型构成。
- Agent 交付任务数汇总。
- 每日交付任务数与日有效 Agent 数图。
- 交付任务类型构成。

当前不会按部分日期重新分摊的周级字段：

- 周验收 GMV。
- 周有效 Agent。
- 单个有效 Agent 周均 GMV。
- 周异构 Agent 比例。
- 分类交付金额。
- 分类质检通过率。
- 待结算费用。

也就是说，只要某一周仍在 `weeks` 数组中，即使只选择该周的部分日期，以上周级字段仍显示整周值。若后续要求所有模块严格跟随任意日期范围，需要补充日级 GMV、日级去重有效 Agent、日级质检和日级交付方式原始数据，不能仅靠当前周总量可靠反推。

平台累计规模不随下方日期选择变化，并在 Mock 服务运行期间每 5 分钟刷新。下方经营数据仍截止 `2026-09-06`，因此累计订单等顶部指标会大于下方六周合计。

## 10. 当前口径的使用边界

1. **经营周报数据与平台累计数据应分开理解**：经营周报截止 `2026-09-06`；平台累计截止 `2026-09-13`，其中后一周是复用最近完整周规模的 Mock 延伸数据。
2. **任务主单与执行订单不能混用**：10,834 是任务主单，16,251 是经营交付/执行。
3. **有效 Agent 不可跨日或跨周直接相加**：它是周期内去重或推导的参与规模。
4. **异构比例不是由页面上的类型构成反算**：当前是独立周级输入。
5. **质检通过率承担了“自动交付金额占比”的含义**：这是当前展示规则；真实系统上线前应确认业务上二者是否确实等价。
6. **待结算费用不是财务流水余额**：当前仅按交付方式和固定比例推导。
7. **顶部累计订单与 Agent 交付任务量的更新频率不同**：下方六周交付量截至 `2026-09-06`，为 16,251；顶部加上 9 月 7–13 日 Mock 延伸周后以 20,795 为初始值，并继续增加仅用于实时展示的 5 分钟增量。该增量不属于可追溯业务明细。
8. **当前数据不应作为审计或结算依据**：展示 Mock 应在接入真实数据仓库后由统一指标服务替换。

### 11.3 结论

当前实现已经做到“周总控和六周累计一致”，但没有做到“日明细一致”。因此：

- 近六周周级图表以及顶部累计规模截至 9 月 6 日的基础部分可以按 Excel 总控解释；顶部 9 月 7–13 日增量是 Mock 延伸，不能标记为 Excel 原始数据。
- 每日图表、日期选择后的局部汇总、任务日分类下钻和验收日分类下钻目前只能视为另一套模拟拆分，不能声称来自 5.1 Excel。
- 如果继续以 Excel 为主，下一步应直接固化或导入 5.1 的 42 天日明细及 252 个日期分类组合，而不是继续用独立哈希算法重算。
- 自动/人工交付记录数应按 Excel 的日分类记录数分配；金额仍以 4.0 的分类 GMV与质检率为控制数。

## 12. 接入真实后端时建议保留的字段定义

| 页面字段 | 建议真实来源 |
| --- | --- |
| 累计成交金额 | 验收通过且计入 GMV 的订单事实表求和 |
| 累计订单 | 执行订单事实表按统一订单定义计数 |
| 累计任务数量 | 排除已删除任务后的任务主表计数 |
| Agent 数量 | Agent 主表按有效注册/激活定义去重 |
| 新增 Agent | Agent 创建时间按日统计 |
| 有效 Agent | 周期内发生有效交付的 Agent ID 去重 |
| 验收 GMV | 验收通过订单金额按验收通过时间统计 |
| 交付任务数 | 执行提交记录按提交时间计数 |
| 质检通过率 | 质检通过执行数 / 已完成质检执行数 |
| 自动/人工交付金额 | 按真实交付方式对验收通过金额分组求和 |
| 待结算费用 | 结算规则引擎或待结算流水的真实余额 |

真实接口还应统一明确时间字段、状态口径、去重主键、退款/申诉回滚规则和时区，保证 Dashboard、任务列表、订单列表与资金模块可以相互核对。
