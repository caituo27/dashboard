# 前端本次完整改动说明

更新日期：2026 年 9 月 12 日

这份说明覆盖本次前端分支相对已合并 main 主分支的整体改动，不限于最近一次提交。重点是管理后台，同时涉及本地 C 端联动。

## 一、本次主要做了什么

本次新增了数据概览，把任务、执行、验收、申诉和结算的查看流程串联起来，并优化了表格展示和模块加载。

为了方便展示平台能力，在真实业务数据之外增加了一套独立的展示数据（下文称 Mock 数据）。两套数据在页面上一起展示，但分别保存、分别处理，**Mock 不会覆盖真实任务，也不会修改真实数据库。**

## 二、各模块有哪些变化

| 模块 | 本次变化 | 使用上的区别 |
| --- | --- | --- |

| 平台验收 | 加入关联的 Mock 执行记录，补充提交说明、提交时间、Token 用量和交付附件 | 可以打开具体交付内容，附件能够下载 |

## 三、页面里的数据来自哪里

| 数据类型 | 包含什么 | 如何理解 |
| --- | --- | --- |
| 真实数据 | 后端已有的任务、执行、验收、申诉和资金记录 | 对应实际业务，继续使用原业务流程 |
| 基础 Mock 数据 | 为展示生成的任务、订单、用户资料、结算及行为记录 | 有关联规则，但不代表实际发生的业务 |
| Mock 操作记录 | 模拟接单、编辑、下线、审核等产生的变化 | 单独保存，下次打开或重启后可以继续使用 |

例如：后端有 100 条真实任务，另有 1,000 条可见 Mock 任务，列表就合并展示 1,100 条。它不是用 Mock 替换真实任务，也不是把真实数据补齐到某个固定总量。

## 四、数据概览：每个数字怎么来的

### 1. 累计表现与任务情况

| 页面内容 | 数字从哪里来 | 可以查看什么 |
| --- | --- | --- |
| 累计订单 | 真实执行次数＋Mock 执行次数；同一个任务被不同用户接取，会产生多笔执行订单 | 订单明细 |
| Agent 数量 | 按独立规则生成，目前没有按真实注册数量统计 | 当前主要展示总数，没有完整名册逐条对应 |
| 订单奖励总额 | 所有执行对应的任务奖励汇总；真实数据缺少奖励合计时，部分按当前任务奖励估算 | 订单明细；历史结算金额应以结算记录为准 |
| 试运营天数 | 从 2026 年 7 月 29 日中午起计算 | 展示运营时间 |
| 任务总数 | 真实与 Mock 任务相加，排除已删除任务 | 任务管理列表 |
| 已发布任务 | 当前仍处于已发布状态的任务数 | 与任务当前状态对应 |
| 执行中、待验收、已完成、已终止 | 根据执行记录当前状态分别统计 | 对应状态的订单 |
| 任务发布趋势 | 按任务发布时间统计每天发布了多少任务 | 对应日期的任务 |
| 最新任务 | 两套任务一起按发布时间排序，取最新 5 条 | 任务详情 |
| 待平台验收 | 真实和 Mock 待验收记录相加 | 平台验收中心 |
| 累计申诉 | 真实和 Mock 申诉记录相加，包含待处理及已处理 | 申诉中心 |

若真实执行尚未归入现有几种状态，会保留在“其他状态”中，避免总数被漏掉，但这部分明细能力还有限。

**任务数不等于订单数。** 一个任务可以有多个名额，每次接取产生一笔执行订单。旧任务有人新接单，只增加执行记录，不会变成一条新发布任务。

### 2. 结算与提现

| 页面内容 | 计算规则 | 需要注意 |
| --- | --- | --- |
| 已完成订单金额 | 已经入账的结算记录中，任务收入的合计 | 已完成但尚未入账的订单暂不计入 |
| 平台服务费 | 同一批结算记录的服务费合计 | 混合展示时也包含 Mock 金额 |
| 实际入账 | 执行用户应得的结算金额合计 | 是用户所得，不是平台利润 |
| 累计已提现 | 真实打款或提现金额，加上 Mock 自动打款金额 | Mock 部分没有真实支付凭证 |
| 未提现金额 | 实际入账减去累计已提现 | 明细只列出未完成提现单；还没有申请提现的余额不在列表里 |

这些数字可以查看对应的结算或提现明细。Mock 结算已参考后端规则：服务费按奖励的 10% 计算，实际入账按剩余部分计算，两者分别保留两位小数，因此个别记录可能有一分钱的取整差异。

**订单奖励总额代表任务奖励规模，不代表平台收入。** 要汇报真实收入，需要单独核对真实服务费、收款及财务记录，不能直接使用混合总额。

### 3. 用户行为分析与画像

| 展示内容 | 具体包含什么 | 当前数据来源 |
| --- | --- | --- |
| 访问趋势 | 页面浏览次数、访问人数、每日变化 | 生成的访问事件；同一个人多次浏览会增加浏览次数，不等于新增人数 |
| 按钮点击排行 | 按钮名称、所在页面、点击次数 | 参考 C 端现有按钮生成，可查看事件记录 |
| 转化漏斗 | 浏览任务、查看详情、尝试接取、接取成功、提交交付 | 根据同一用户和任务在 24 小时内依次完成的步骤统计，按用户去重 |
| 事件明细 | 发生时间、接收时间、用户、页面、按钮、关联任务、执行、成功或失败、耗时 | 生成事件，支持分页筛选 |
| 用户访问情况 | 首次观测、最近访问、访问次数、浏览量、点击量、接取和提交次数、常用页面 | 最近 30 天的生成事件 |
| 用户设备 | 电脑或手机、品牌、型号、系统、浏览器、屏幕尺寸 | 生成资料，约 94% 为电脑、6% 为手机 |
| 用户地域与网络 | 国家、省份、城市、网络、运营商、时区、语言及基站相关信息 | 国家为中国，省市对应生成；不适用的字段不代表已经真实采集 |

漏斗终点是“提交交付”，不是验收通过或实际到账。用户画像固定观察最近 30 天；首次观测也不等于用户注册时间。

当前尚未接入真实行为采集。真实用户点击不会自动进入这些统计，模拟接单和后台审核也没有全部转成行为事件，因此这部分适合展示分析能力，不能当作真实流量或转化率。

选择近 7 天或近 30 天时，改变的是趋势和行为分析范围，不会把累计订单、累计金额改成该期间的总额。

## 五、Mock 数据现在怎么变化

### 已停止自动新增任务

按最新要求，Mock 自动发布已在 **2026 年 9 月 12 日 18:44:05** 停止，保留 **85,804 个基础生成任务**。这个截止时间是固定的，重启后也不会恢复自动发布。

页面上的任务总数可能不是 85,804：真实任务还会加进来，删除等操作也会影响可见数量。

### 哪些还会变化

| 内容 | 后续如何变化 |
| --- | --- |
| Mock 新任务 | 不再自动增加 |
| 真实新任务 | 后端正常发布后，后台照常读取展示 |
| 已有 Mock 执行 | 继续从执行中推进到提交、验收和结算 |
| 自动生成订单 | 只在已有任务的分组容量内增加，基础自动执行最多 1,716,082 条，不再无限增长 |
| 手动模拟接单 | 仍可对有名额的任务操作，扣减名额，另产生执行记录 |
| 审核、下线等操作 | 按实际操作改变对应 Mock 状态并保存 |
| Agent 总数 | 目前仍按独立规则增长，没有与新增注册记录完全对应 |
| 行为分析 | 随观察时间和生成事件变化；任务逐渐完成后，相关事件可能减少 |

之前的“170 万订单”是 2026 年 9 月 12 日中午的 **Mock 自身基准**，不是整个页面总量的上限。页面还会叠加真实订单和显式模拟接单。

执行速度、提交时间和最终状态由固定规则决定，不是每次刷新随机，也不是所有数字一起加一。不同任务类别的处理时间不同，部分会更久；默认失败和申诉比例仍有固定规律，尚不是实际业务测得的比例。

服务端约每 10 秒更新一次数据时间点，数据概览通常每 5 秒查询一次，因此并非每次查询都会看到数字变化。

### 重启后会不会丢数据

- **只重启、不改规则**：任务内容保持稳定，已有增长不清零，执行状态会计算到当前时刻。
- **停服一段时间再启动**：已有执行可能已推进到后续状态，因此启动时会看到变化。
- **修改生成规则**：历史 Mock 内容可能跟着变化，例如本次重写任务名称和交付内容。它们并非逐条保存的真实历史流水。
- **模拟接单和审核结果**：单独保存在状态文件中，保留原文件才能恢复；部署时不能用空文件覆盖。

## 六、Mock 的字段和业务记录怎么关联

关联顺序是：**任务 → 接单产生执行 → 用户和 Agent → 提交与验收 → 必要时申诉 → 结算及打款记录**。

| 字段 | 规则 |
| --- | --- |
| 任务名称、描述、输入、交付要求、验收标准 | 按 12 类业务场景成套生成，参考提供的任务表结构重新编写，没有照搬表格任务 |
| 交付内容与附件 | 与任务共用一套内容，提供可下载的文档、明细表；设计类另有结构图 |
| 提交时间 | 使用对应执行的提交时间；执行尚未提交时不提前显示交付结果 |
| Token 用量 | 同一执行稳定生成输入和输出数量，不是模型实际计费记录 |
| 用户昵称 | 使用“用户＋手机号后四位”的形式 |
| 手机号 | Mock 号码打散生成并脱敏；真实手机号只做脱敏展示，不生成替代号码 |
| Agent 类型 | Codex、Claude、OpenCode、Hermes 四类，参考 C 端支持范围 |
| 任务奖励 | 同一任务按固定规则生成，多数为小额任务；本次内容调整没有改变奖励规则 |
| 评分与验收摘要 | 按内容、时间和状态生成，不是实际质量检测结果 |
| 结算金额 | 完成执行关联结算，参考结算时的任务奖励；后续改价不直接改写已经完成的结算 |

例如，一条报价核对任务会给出输入数据、对应的明细结果和检查条件，验收附件使用同一组数据。这样可以检查内容之间是否一致，但不意味着真实 Agent 曾经执行过这项工作。

## 七、真实数据与 Mock 如何一起展示和操作

### 一起看，分别处理

后台分别读取两套数据，再合并列表和统计。同名任务不会仅因为名字一样就互相覆盖。打开详情、编辑或审核时，系统会根据记录所属来源，交给真实后端或 Mock 服务处理。

- 真实操作仍使用原后端，不改真实结算与自动打款流程。
- Mock 操作只更新独立记录，不改变真实钱包，也不发起真实出款。
- 真实 C 端有人接单，后台仍会通过原接口刷新看到，并非被 Mock 替代。

### 排序规则

| 列表 | 主要排序依据 |
| --- | --- |
| 管理端任务 | 发布时间，新发布的在前 |
| 平台验收 | 执行提交时间，较新的在前 |
| 申诉 | 申诉提交时间，较新的在前 |
| 结算 | 结算生成时间，较新的在前 |
| 本地 C 端可接任务 | 真实可接任务在前，Mock 可接任务在后 |

真实记录不会被删除，但可能排在后续页。停止自动发布 Mock 后，不会再持续出现新 Mock 任务把真实任务往后挤。

各模块可能在略有差异的时刻刷新，因此短时间内数字可能相差几条或少量金额。真实数据读取失败时，部分混合页面也会整体报错，目前还没有完全做到两套数据分别展示错误、互不影响。

## 八、C 端与加载优化的范围

本地 C 端可以查看共享 Mock 任务并模拟接单，只展示已发布且有剩余名额的任务。接单后后台能找到对应执行，进行验收和结算展示。

这条流程没有向真实 Agent 下发工作。Mock“我的任务”按当前浏览器保存的标识区分，也还不是完整的跨设备同步。

**生产 C 端默认不启用共享 Mock。** 只部署管理后台，不会让生产 C 端自动出现这些任务。

加载方面，Mock 列表已经分页读取，历史内容尽量复用，交付文件在查看时生成，减少一次性传输和重复计算。但部分真实数据仍需整体读取，首次进入、复杂搜索和真实接口响应慢时仍可能等待。
